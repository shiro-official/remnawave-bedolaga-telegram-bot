# Разделение обычного и БС-трафика: backend-этапы

Эта ветка добавляет хранение настроек, подготовку вторичной учётки и внутренний
сервис объединения конфигураций с общей политикой устройств и защищённым
публичным маршрутом, выключенным по умолчанию. Она ещё не включает разделение
у пользователей: перенос/активация, жизненный цикл, покупки и интерфейсы требуют
следующих этапов. Установка этой версии сама по себе не создаёт WL-учётки,
не меняет сквады и пользовательские ссылки. Одного включения маршрута также
недостаточно: неактивные ключи доступа не принимаются.

## Данные и совместимость

Миграция Alembic `0132` следует за `0131`:

- В тариф добавлены `bs_traffic_enabled`, `bs_traffic_limit_gb`, `bs_squad_uuids`.
  По умолчанию функция выключена; обычный лимит и выбранные сквады сохранены.
- `subscriptions.traffic_mode` по умолчанию равен `shared`. Перевод в `split`
  должен быть отдельным подтверждённым переходом после готовности всей выдачи.
- `subscription_bs_accounts` хранит вторичный panel id, short UUID, постоянное
  имя, маркер восстановления, отдельные лимит/расход и стадию подготовки.
  На одну подписку разрешена одна БС-запись. Первичная идентичность остаётся
  в существующих полях пользователя/подписки.
- Новая таблица включена в штатный backup/restore после родительской подписки.

Миграция не меняет пользователей, балансы, платежи, сроки или ссылки. Общий
исторический расход не выдаётся за раздельный БС-расход. Переход существующих
платных подписок на новую схему остаётся в общем плане проекта; это не режим
«только для новых пользователей». Триал сохраняет общие 50 ГБ.

Обратная миграция удаляет новую таблицу с её данными. Это технический откат
схемы, а не способ безопасно откатить уже включённую услугу: рабочее внедрение
требует свежих резервных копий и согласования состояния самой панели.

## Проверка разделения

`bs_traffic_policy.resolve_bs_plan` допускает только периодный тариф с обычным
безлимитом, положительным БС-лимитом и отдельными группами сквадов. Триал и
тариф без включённого БС сохраняют прежнее поведение. Суточные, мультитарифные
и произвольно выбираемые объёмы трафика не включаются неявно.

Названия `Classic`, `White`, `CDN White`, `Trial` не используются как признаки
доступа. План строится по UUID. `validate_bs_inbounds` читает реальные inbound
UUID у выбранных сквадов и запрещает пересечение групп, включая обход через
сквад Trial. Пустой, отсутствующий или некорректный сквад не проходит проверку.

## Подготовка учётки

`bs_subscription_service.prepare_bs_account` — отдельная операция подготовки,
которая владеет своими транзакциями. Она не подключена к оплате, startup,
админским маршрутам или автоматической миграции пользователей.

1. Блокирует родительскую подписку и проверяет конфигурацию/inbounds.
2. Сохраняет стабильное имя и маркер намерения **до** обращения к панели.
3. Через общий `panel_sync.writer` создаёт или восстанавливает только свою
   вторичную учётку в состоянии `DISABLED`.
4. Проверяет ответ панели: идентичность, отключённое состояние, БС-сквады,
   отдельный лимит и стратегию сброса. Только затем сохраняет panel id и
   состояние `prepared`. Неподтверждённая запись остаётся `pending` для повтора.

Потеря ответа после успешного создания не требует второй учётки: следующая
попытка находит собственную запись по сохранённому имени и маркеру. Таймаут
чтения не считается доказательством отсутствия пользователя. Чужое совпавшее
имя не присваивается. Уже включённый аккаунт подготовкой не отключается.

Telegram ID и email не копируются во вторичную учётку: связь с владельцем
явно хранится в БД. Это также не даёт старому поиску по Telegram/email случайно
выбрать её вместо основной. Общие проверки идентичности дополнительно
запрещают записать зарезервированный БС-id в первичную подписку/пользователя,
даже если это тот же владелец или ошибочный сохранённый указатель.

При подготовке не меняются первичные сквады, ключи, лимит, расход, дата и
пользовательская ссылка. Персональный БС-лимит не затирается лимитом тарифа.
Подготовка не является включением услуги и не заменяет общий контроль HWID.

## Внутренняя выдача и объединение

`app/services/bs_subscription_delivery.py:deliver_subscription` — внутренний сервис.
Он принимает **уже авторизованный** внутренний
id подписки; сам id не является секретом и не может служить публичным токеном.
Наружу он не открывается по числовому id. Для HTTP используется отдельный
`deliver_public_subscription`, который проверяет секрет и привязку под блокировкой.

Проверяется активность владельца/подписки, срок, точный основной panel id и
short UUID, включая резервирование id вторичной ролью. До обращения к WL
загружается основной публичный ответ. При HTTP-отказе, `x-hwid-limit`,
`x-hwid-not-supported` или `x-hwid-max-devices-reached` WL даже не запрашивается.
`x-hwid-active=true` сам по себе не считается разрешением. Регистр заголовков
нормализуется; неизвестное значение флага отказа трактуется как отказ.

Для платной подписки в `split` объединение разрешено только с WL-записью
`active`, точными id/short UUID/именем/маркером владения, действующим сроком и
неисчерпанной квотой панели. Также проверяется, что WL не закреплён как основная
учётка пользователя или другой подписки. При ошибке WL основной ответ сохраняется.
Триал и `shared` получают только основной ответ. Сервис не меняет данные БД и
не коммитит входную транзакцию; грязная транзакция отвергается до autoflush.
Для `split` используется собственная короткоживущая транзакция блокировки и
свежий снимок подписки после получения блокировки.

Ответы-заглушки панели могут быть валидными конфигурациями и приходить до
проверки HWID, например при `respondWithRemarks`. Поэтому для объединения
дополнительно требуется наличие в каждом документе реального VLESS/VMess,
Trojan или Shadowsocks-ключа соответствующего аккаунта. Нулевой UUID штатной
заглушки не подходит. Это проверка конфигурации, а не универсальное доказательство
допуска: произвольные пользовательские response rules, custom remarks с реальными
ключами и внешние шаблоны обязательно проверяются отдельно до включения.

`app/services/bs_subscription_composer.py` поддерживает:

- Обычные списки URI и base64 от них: сохраняется кодирование основного ответа,
  точные повторения ссылок удаляются, ключи не переписываются.
- Xray JSON: целые профили помещаются в общий массив без изменения внутренних
  tags, DNS, маршрутизации, transport settings или ключей. Sing-box JSON не
  принимается за Xray и пока не объединяется.
- Clash/Mihomo: только совместимые шаблоны с явными списками `proxies` в группах,
  одинаковыми общими настройками и группами. Добавляются WL-прокси и их членство
  в соответствующих группах. При совпадении имён WL получает стабильный суффикс
  `[БС]` (с номером при дополнительном конфликте). Обычные имена сохраняются.
  Динамические фильтры, provider selectors, YAML aliases, `dialer-proxy`, прямые
  ссылки на имена отдельных прокси в правилах и несовместимые шаблоны пока
  возвращают исходный основной документ без WL.

Неподдерживаемый/повреждённый формат не преобразуется с потерей настроек.
Результат содержит `bs_included` и код причины без конфигураций/ключей для
будущей диагностики. Верхний `subscription-userinfo` берётся из основной
подписки: БС-квота не превращает обычный безлимит в общий лимит. Отдельный
счётчик БС будет доступен через API/интерфейсы на следующем этапе.

Новый метод транспорта `get_public_subscription_response` читает только
проверенный short UUID на настроенном адресе панели, не следует редиректам,
сохраняет HTTP-статус и ограничивает ответ 4 МиБ, в том числе без Content-Length.
В клиентском ответе остаются разрешённые заголовки профиля/квоты/отказа и
`Cache-Control: no-store, private`; cookies, старые ETag/Content-Length и
служебные заголовки панели не передаются. Клиент может передать панели только
User-Agent и четыре HWID/device-заголовка, предусмотренных текущим контрактом
(включая сам `x-hwid`); Authorization, Cookie и proxy headers от клиента исключены.

## Общие устройства и слоты

`app/services/bs_device_policy.py` использует основной панельный HWID-реестр как
единственный источник допуска. Отдельный независимый пул слотов для WL не
выдаётся; третья копия реестра в БД бота не создаётся. Реализация ориентируется
на контракт Remnawave 3.4.5: обычная публичная выдача нового HWID использует
атомарный `CreateWithAdvisoryLock`, а административное создание устройства
такой гарантии не предоставляет. Административное создание здесь не используется.

Для конечного лимита нужны все подтверждения: явный положительный
`primary.hwidDeviceLimit`, допустимый `x-hwid`, реальный основной конфиг,
отсутствие отказа, `x-hwid-active=true` и наличие устройства в полном основном
реестре после публичного запроса. Затем:

1. Из WL удаляются HWID, которых нет в основном реестре. Успех удаления
   подтверждается повторным чтением, даже если панель вернула положительный ack.
2. В WL узкой записью через `panel_sync.writer` копируется фактический основной
   лимит. Не базовый лимит тарифа: купленные слоты и личные настройки основного
   аккаунта сохраняются. Основной лимит, квота БС, ключи, срок, статус и сквады
   этой операцией не меняются. Перед записью повторно проверяется владелец WL;
   ответ должен подтвердить новый лимит и ту же идентичность.
3. WL проходит собственную штатную публичную проверку HWID. Она не выключается
   и не подменяется административным добавлением устройства.
4. Перед отправкой БС-ключей снова проверяются HWID-флаги и оба реестра: WL
   должен быть подмножеством основного, запрошенный HWID — присутствовать в обоих.

`hwidDeviceLimit=0` сохраняет существующий явно заданный безлимит устройств,
включая клиентов без HWID. `null`, наследуемый/неопределённый fallback, выключенная
проверка при конечном лимите, неполный/повреждённый список или неизвестный
владелец устройства не считаются подтверждением: ответ остаётся обычным, без БС,
с причиной `device_policy_unconfirmed` либо ошибки идентичности/панели. Список
должен соответствовать непагинируемому контракту `{total, devices}`: число,
полный массив, уникальные корректные HWID и правильный числовой `userId`.

При снижении лимита вручную панель может сохранять уже зарегистрированные
устройства сверх нового значения. Бот не расширяет WL-лимит ради обхода этого
случая: WL вправе отказать отсутствующему в своём реестре устройству. Обычный
доступ при этом сохраняется; штатные операции уменьшения слотов удаляют лишние
устройства согласованно из двух аккаунтов.

Выдача `split`, удаление и сброс сериализованы PostgreSQL advisory-lock по id
подписки. Блокировка живёт в отдельной сессии, не коммитит и не делает autoflush
работы вызывающего кода, освобождается при отмене/ошибке. Разные подписки не
блокируют друг друга; ожидание ограничено 5 секундами. SQLite не используется
как имитация распределённой блокировки для `split`.

Соединение этой сессии открывается отдельно по тому же PostgreSQL URL и
закрывается при выходе (`NullPool`). Оно не занимает второй слот в уже занятом
пуле вызывающего кода: проверен в том числе пул размером в одно соединение.
При расчёте общего `max_connections` PostgreSQL нужно учитывать эти временные
соединения согласования наряду с основным пулом бота.

`remove_subscription_device` и `reset_subscription_devices` подключены к
Telegram, кабинету, админским маршрутам, миниаппу, уменьшению слотов и штатным
сбросам при продлении/смене тарифа/очистке. Для сохранённой `shared`-подписки
остаётся прежняя операция на одной учётке. Режим проверяется заново под
блокировкой для реальных PostgreSQL/ORM-вызовов; устаревший объект `shared`
не позволяет пропустить уже сохранённый WL. Входная оплата/правки не коммитятся.

Удаление/сброс выполняются сначала в WL, затем в основном аккаунте, с проверкой
состояния после каждого запроса. При отказе WL основной реестр не очищается.
Частичный результат не выдаётся за успешный сброс; повтор идемпотентен. Пустой
основной список не отменяет очистку устаревшего WL. Как и в исходном боте,
сброс регистрации освобождает слот, но не запрещает устройству снова загрузить
подписку и не отзывает уже выданные VPN-ключи.

Прямые изменения через панель находятся вне блокировок бота; несогласованность
проверяется перед выдачей БС и исправляется при следующем запросе. До включения
нужны проверка реальных response rules/внешних сквадов, непубликация прямой
WL-ссылки, координация смены режима/ключей/учёток той же блокировкой и проба
на реальных Remnawave/Happ. Исходники отдельной страницы подписки пока отсутствуют.

## Защищённая общая ссылка

Миграция `0133` после `0132` добавляет `subscription_public_links` с уникальными
`subscription_id` и SHA-256-хешем случайного ключа. Она не создаёт ссылки и не
меняет существующие записи пользователей. Таблица включена в backup/restore.
В ней хранятся привязки к точным id/short UUID двух аккаунтов, флаг включения
и состояние незавершённого перевыпуска. Сам случайный ключ в этой таблице не
хранится; опубликованный URL, как и прежде, находится в `subscriptions.subscription_url`
и является секретом владельца. Backup с этими URL требует прежней защиты доступа.

`prepare_public_link` создаёт отключённого кандидата с 256-битным случайным
ключом (`secrets.token_urlsafe(32)`). Подготовка не публикует его, не меняет
пользовательский URL/сквады и не активирует аккаунты. Активный ключ или pending
перевыпуск ей перезаписать нельзя. Повтор после потерянного ответа подготовки
заменяет только отключённого кандидата. Включение кандидата будет частью
ещё не подключённого процесса переноса; текущая версия не включает его автоматически.

Настройки (`.env.example`):

- `BS_SUBSCRIPTION_DELIVERY_ENABLED=false` — маршруты не монтируются.
- `BS_SUBSCRIPTION_PUBLIC_BASE_URL` — явный HTTPS origin без пути, credentials,
  query/fragment. Пустое значение при выключенной функции допустимо. Неправильное
  значение при явном включении останавливает запуск; домен не угадывается.
- `BS_SUBSCRIPTION_IP_RATE_LIMIT=120`, `BS_SUBSCRIPTION_TOKEN_RATE_LIMIT=60` —
  ограничения за 60 секунд через Redis с fail-closed при его недоступности.
- `BS_SUBSCRIPTION_MAX_CONCURRENT=8` — предел одновременных загрузок на процесс,
  ожидание свободного места до одной секунды. Дополнительные соединения guard/work
  с БД нужно учитывать в общем бюджете PostgreSQL.

При включённой конфигурации unified server обслуживает `GET /s/{token}` и
`GET /s/{token}/{client_type}`, независимо от включения административного API.
Разрешены только типы Remnawave 3.4.5: `json`, `v2ray-json`, `clash`, `mihomo`,
`stash`, `singbox`; они передаются обеим учёткам как проверенный сегмент пути.
Список разрешённых адресов форматов не расширяет возможности объединителя:
Sing-box и несовместимые шаблоны пока сохраняют только основной документ.
Основной путь выбирает формат по исходному User-Agent панели.

Числовой id, primary short UUID и адрес upstream из запроса не принимаются как
публичные credentials. Неизвестный/закрытый/отозванный ключ и нарушенная привязка
дают одинаковый 404. Первичный поиск хеша повторно подтверждается под общей
блокировкой выдачи/сброса/перевыпуска; уже начавший поиск запрос не может получить
новые ключи после отзыва старого секрета. Проверяются `split`, отсутствие триала,
активность WL и точные привязки обеих идентичностей, затем обычная политика доступа.

Не передаются query-параметры и клиентские proxy/authorization headers. IP берётся
из `request.client`, а доверенные proxy headers должен обрабатывать настроенный
ASGI server. На production ingress нужно правильно настроить доверенные proxy/IP
и отключить/маскировать access-логи для `/s/`: URL содержит секрет. Новые пути
исключены из OpenAPI. В приложении путь, включая ошибки и mount prefix, маскируется
в middleware и контексте журнала действий; сообщения исключений на секретном пути
не печатаются. Redis получает хеш ключа, не исходный токен.

Успехи и ошибки имеют `Cache-Control: no-store, private`, `Referrer-Policy:
no-referrer`, `nosniff` и запрет индексации. При отказе лимитера — 429, недоступности
панели/БД — 503 без upstream-текста, SQL-параметров и секретов. HTML панели
не отдаётся как общая страница: её import-кнопки ведут в primary-only URL.
Вместо этого маршрут возвращает 406 с предложением открыть ссылку в VPN-клиенте.
Существующая брендированная страница не заменяется; её исходники и ingress
по-прежнему нужны для полноценного браузерного подключения.

Обычная синхронизация, panel push и webhook перевыпуска сохраняют опубликованный
общий URL и его cryptolink. Изменение panel short UUID при этом остаётся настоящим
изменением идентичности: несовпавшая сохранённая привязка закрывает старый доступ,
а не молча переадресует старый секрет к новым ключам. Окончательную координацию
всех lifecycle/import/webhook-сценариев нужно закончить до рабочего переноса.

## Перевыпуск общей ссылки и ключей

Штатный `SubscriptionService.revoke_subscription`, используемый ботом и кабинетом,
для `shared`/триала сохраняет прежнее поведение. Для активной общей `split`-ссылки
он вызывает `revoke_split_public_link`:

1. Под той же PostgreSQL-блокировкой проверяются точные владельцы/привязки обеих
   учёток. В независимой work-сессии коммитятся отключение старого ключа и намерение
   перевыпуска до первого API-запроса изменения. Commit намерения не отпускает guard.
2. Заранее сохраняются два разных новых panel short UUID и хеши старых credentials.
   Сначала меняются ключи/ссылка WL, потом основной учётки. API-ответ и отдельное
   чтение должны подтвердить целевой short UUID и смену всех ранее известных ключей.
3. При потерянном ответе повтор проверяет сохранённые цели и текущие ключи. Уже
   подтверждённое действие не выполняется повторно; неподтверждённое можно повторить.
   Старый публичный ключ остаётся закрыт при любом частичном отказе.
4. После подтверждения обеих учёток атомарно публикуются новый случайный общий
   URL, его хеш/привязки и дата cooldown. Старая криптоссылка не сохраняется; если
   выбран Happ cryptolink, шифруется только новый общий URL. При ошибке шифрования
   остаётся штатный fallback к обычному общему URL. Прямые WL-URL не шифруются.

Методы identity-read, подготовки WL, синхронизации её device limit и парного revoke
выключают Happ-enrichment в API-клиенте. Это также исключает ненужную отправку
технической ссылки во внешний Happ API при выбранном cryptolink-режиме. Обычные
primary-вызовы API сохраняют прежнее поведение.

Деньги, срок, квота, расход и выбранные сквады этим процессом не изменяются.
Привычный cooldown действует после успешного перевыпуска; pending-попытку можно
восстановить, повторный конкурентный вызов в cooldown возвращает уже готовый URL.
Функция не активирует отключённых кандидатов и не заменяет миграцию/перенос.
Downgrade `0133` удаляет токены/намерения, но не возвращает уже заменённые ключи
панели и не является способом операционного отката включённой услуги.

## Проверки

Для новых проверок и регрессий синхронизации нужен отдельный PostgreSQL:

```sh
TEST_DATABASE_URL=postgresql+asyncpg://test:test@127.0.0.1:55432/test \
REQUIRE_POSTGRES_TESTS=1 uv run pytest -q \
  tests/services/test_bs_traffic_policy.py \
  tests/database/test_bs_account_preparation_postgres.py \
  tests/database/test_bs_traffic_migration_postgres.py \
  tests/services/test_bs_subscription_composer.py \
  tests/database/test_bs_subscription_delivery_postgres.py \
  tests/external/test_bs_public_subscription_transport.py \
  tests/services/test_bs_device_policy.py \
  tests/database/test_bs_shared_devices_postgres.py \
  tests/contracts/test_device_mutation_surfaces_use_shared_policy.py \
  tests/services/test_bs_public_link_tokens.py \
  tests/database/test_bs_public_links_postgres.py \
  tests/database/test_bs_public_link_migration_postgres.py \
  tests/webserver/test_bs_subscription_router.py \
  tests/external/test_bs_identity_no_cryptolink.py \
  tests/services/panel_sync
```

В cloud-среде тестовые сервисы поднимаются сохранённой инструкцией среды.
Никогда не указывайте production БД в `TEST_DATABASE_URL`: фикстуры пересоздают
тестовую схему. Панель в этих тестах заменена управляемым тестовым клиентом;
live Remnawave, VPN и Happ этими результатами не проверены.

Перед рабочим переносом остаются обязательными: production ingress/страница, проверка
клиентских форматов/устройств на стенде, переключение сквадов, маршрутизация
webhook по роли, докупки/продления/смена тарифа, отзыв и удаление, двусторонняя
синхронизация, API/Telegram и frontend. Эта ветка пока не является полной
БС-функцией и не предназначена для включения на рабочих подписках.
