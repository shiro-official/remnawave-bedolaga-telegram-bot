# Разделение обычного и БС-трафика: первый backend-этап

Эта ветка добавляет хранение настроек и подготовку вторичной учётки. Она ещё
не включает разделение у пользователей: объединитель, общий контроль устройств,
покупки и интерфейсы подключаются следующими этапами. Установка этой версии
сама по себе не создаёт WL-учётки и не меняет сквады.

## Данные и совместимость

Миграция Alembic `0132` следует за `0131`:

- В тариф добавлены `bs_traffic_enabled`, `bs_traffic_limit_gb`, `bs_squad_uuids`.
  По умолчанию функция выключена; обычный лимит и выбранные сквады сохранены.
- `subscriptions.traffic_mode` по умолчанию равен `shared`. Перевод в `split`
  должен быть отдельным подтверждённым переходом после готовности всей выдачи.
- `subscription_bs_accounts` хранит вторичный panel id, short UUID, постоянное
  имя, маркер восстановления, отдельные лимит/расход и стадию подготовки.
  На одну подписку разрешена одна БС-запись. Первичная идентичность остаётся
  в существующих полях пользователя/подписки.
- Новая таблица включена в штатный backup/restore после родительской подписки.

Миграция не меняет пользователей, балансы, платежи, сроки или ссылки. Общий
исторический расход не выдаётся за раздельный БС-расход. Переход существующих
платных подписок на новую схему остаётся в общем плане проекта; это не режим
«только для новых пользователей». Триал сохраняет общие 50 ГБ.

Обратная миграция удаляет новую таблицу с её данными. Это технический откат
схемы, а не способ безопасно откатить уже включённую услугу: рабочее внедрение
требует свежих резервных копий и согласования состояния самой панели.

## Проверка разделения

`bs_traffic_policy.resolve_bs_plan` допускает только периодный тариф с обычным
безлимитом, положительным БС-лимитом и отдельными группами сквадов. Триал и
тариф без включённого БС сохраняют прежнее поведение. Суточные, мультитарифные
и произвольно выбираемые объёмы трафика не включаются неявно.

Названия `Classic`, `White`, `CDN White`, `Trial` не используются как признаки
доступа. План строится по UUID. `validate_bs_inbounds` читает реальные inbound
UUID у выбранных сквадов и запрещает пересечение групп, включая обход через
сквад Trial. Пустой, отсутствующий или некорректный сквад не проходит проверку.

## Подготовка учётки

`bs_subscription_service.prepare_bs_account` — отдельная операция подготовки,
которая владеет своими транзакциями. Она не подключена к оплате, startup,
админским маршрутам или автоматической миграции пользователей.

1. Блокирует родительскую подписку и проверяет конфигурацию/inbounds.
2. Сохраняет стабильное имя и маркер намерения **до** обращения к панели.
3. Через общий `panel_sync.writer` создаёт или восстанавливает только свою
   вторичную учётку в состоянии `DISABLED`.
4. Проверяет ответ панели: идентичность, отключённое состояние, БС-сквады,
   отдельный лимит и стратегию сброса. Только затем сохраняет panel id и
   состояние `prepared`. Неподтверждённая запись остаётся `pending` для повтора.

Потеря ответа после успешного создания не требует второй учётки: следующая
попытка находит собственную запись по сохранённому имени и маркеру. Таймаут
чтения не считается доказательством отсутствия пользователя. Чужое совпавшее
имя не присваивается. Уже включённый аккаунт подготовкой не отключается.

Telegram ID и email не копируются во вторичную учётку: связь с владельцем
явно хранится в БД. Это также не даёт старому поиску по Telegram/email случайно
выбрать её вместо основной. Общие проверки идентичности дополнительно
запрещают записать зарезервированный БС-id в первичную подписку/пользователя,
даже если это тот же владелец или ошибочный сохранённый указатель.

При подготовке не меняются первичные сквады, ключи, лимит, расход, дата и
пользовательская ссылка. Персональный БС-лимит не затирается лимитом тарифа.
Подготовка не является включением услуги и не заменяет общий контроль HWID.

## Проверки

Для новых проверок и регрессий синхронизации нужен отдельный PostgreSQL:

```sh
TEST_DATABASE_URL=postgresql+asyncpg://test:test@127.0.0.1:55432/test \
REQUIRE_POSTGRES_TESTS=1 uv run pytest -q \
  tests/services/test_bs_traffic_policy.py \
  tests/database/test_bs_account_preparation_postgres.py \
  tests/database/test_bs_traffic_migration_postgres.py \
  tests/services/panel_sync
```

В cloud-среде тестовые сервисы поднимаются сохранённой инструкцией среды.
Никогда не указывайте production БД в `TEST_DATABASE_URL`: фикстуры пересоздают
тестовую схему. Панель в этих тестах заменена управляемым тестовым клиентом;
live Remnawave, VPN и Happ этими результатами не проверены.

Перед включением остаются обязательными: объединённая выдача и форматы
клиентов, общий лимит устройств, безопасное переключение сквадов, маршрутизация
webhook по роли, докупки/продления/смена тарифа, отзыв и удаление, двусторонняя
синхронизация, API/Telegram и frontend. Эта ветка пока не является полной
БС-функцией и не предназначена для включения на рабочих подписках.
